# Building SedSAT3 on Windows with Pixi

**Author:** USGS code review (build-verification notes)
**Date:** 2026-09-14 (revised 2026-10-13)
**Repo state:** superproject `ce7bc1d`; submodules `Utilities @ 5db8d14`, `QXlsx @ 700bda6`

## Purpose

SedSAT3 is distributed for macOS and Linux; the repository provides no
documented Windows-from-source build path. This document records a *working*
Windows build achieved with [pixi](https://pixi.sh) supplying the third-party
libraries and MSVC (Visual Studio 2022) supplying the compiler. It is written
so the procedure is reproducible and so the obstacles encountered are on the
record for the developers (should they wish to support Windows).

The exercise doubles as build-verification evidence for the software code
review: the application compiles, links, and launches on a platform other than
its primary targets, from a declaratively specified environment.

> ### IMPORTANT — this procedure is NOT in the upstream repo
>
> A fresh clone of commit `ce7bc1d` does **not** contain the pixi environment
> or the static-analysis configuration this document relies on. Specifically,
> **none of the following files exist in the upstream tree** and all were
> **created during this review**:
>
> | File | Status in `ce7bc1d` | Role |
> |------|---------------------|------|
> | `pixi.toml` | absent | declares the conda-forge library stack + build/analysis tasks |
> | `pixi.lock` | absent | generated by pixi on first run; do not hand-write |
> | `.clang-tidy` | absent | clang-tidy check selection (repo root) |
>
> Therefore this is a **two-phase** procedure. **Phase A (Setup)** creates the
> files a fresh clone is missing. **Phase B (Build & analyze)** is the actual
> workflow once those files are in place. If you already have a working tree
> that contains these files (e.g. the reviewer's tree), skip Phase A.
>
> The full, authoritative contents of `pixi.toml` and `.clang-tidy` are given
> verbatim in **Appendix A** and **Appendix B** so Phase A is self-contained.

## Prerequisites

- Windows 10/11, x64
- Visual Studio 2022 (Community is fine) with the "Desktop development with
  C++" workload — provides `cl.exe`, `link.exe`, and the VC++ redistributable
- [pixi](https://pixi.sh) (tested with pixi 0.72.0)
- Git

## Phase A — Setup (create what a fresh clone lacks)

Do this once, immediately after cloning. It (1) clones and repairs the
submodules, and (2) drops in the pixi + clang-tidy files that are not part of
the upstream repo.

### A.1 Clone and initialize submodules

```powershell
git clone <repo> SedimentSourceAssessmentTool3
cd SedimentSourceAssessmentTool3
git submodule update --init --recursive     # will FAIL on QXlsx; see Pitfall 1
```

The `--recursive` step **fails** on a fresh clone because the QXlsx submodule
URL in `.gitmodules` is dead — see **Pitfall 1** for the exact repair, and
**Pitfall 2** for the `Utilities` empty-working-tree follow-on. Complete both
before continuing.

### A.2 Create `pixi.toml` at the repo root

A fresh clone has **no** `pixi.toml`, so `pixi run ...` has nothing to execute.
Create the file at the repository root with the exact contents in
**Appendix A**. It declares:

- `qt6-main`, `qt6-charts` — Qt6 Core/Gui/Widgets/PrintSupport/Charts
- `armadillo`, `libblas`, `liblapack`, `openblas` — linear algebra
- `gsl` — GNU Scientific Library
- `cmake`, `ninja` — build tooling
- `clang-tools`, `cppcheck` — static analysis
- the `[tasks]` table (`build`, `deploy-win`, `run-app`, `lint`, `cppcheck`,
  `check`, and the debug-build variants)

The MSVC compiler is intentionally **not** provided by pixi; mixing conda
compilers with a conda Qt on Windows is fragile. MSVC-for-compiler +
conda-for-libraries proved to be the reliable combination.

### A.3 Create `.clang-tidy` at the repo root

Also absent from a fresh clone. Without it, `clang-tidy` runs with **zero**
checks enabled and errors out (see Incantation 2). Create `.clang-tidy` at the
repository root with the exact contents in **Appendix B**.

> `pixi.lock` is **not** created by hand — pixi generates and maintains it the
> first time you run a `pixi` command. Let it be created automatically.

After A.1–A.3 the working tree matches the state the rest of this document
assumes.

## Phase B — Build and analyze

Run from a **"Developer PowerShell for VS 2022"** (so `cl.exe`/`link.exe` — and,
for clang-tidy, the MSVC headers — are on PATH).

```powershell
pixi run build         # configure + compile -> build\bin\SedSat3.exe
pixi run deploy-win    # stage Qt + numerical DLLs next to the exe (optional)
pixi run run-app       # launch inside the activated env (most reliable)
```

Static analysis (details and gotchas in the dedicated section below):

```powershell
pixi run cppcheck      # fast; standalone
pixi run lint          # slower; sourcesinkdata.cpp is ~188 KB
pixi run check         # both
```

## Pitfalls and obstacles (in the order encountered)

### Pitfall 1 — Dead QXlsx submodule URL (blocks everyone, all platforms)

`.gitmodules` points the QXlsx submodule at:

```
https://github.com/j2doll/QXlsx.git      # 404 - repository not found
```

This repository no longer exists at that location. `git submodule update
--init` therefore fails for a fresh clone on **any** platform, which
contradicts the build instructions in `README.md`. The live upstream is:

```
https://github.com/QtExcel/QXlsx.git
```

**Workaround used:** clone QtExcel into the submodule path and check out the
exact commit the superproject pins:

```powershell
git clone https://github.com/QtExcel/QXlsx.git thirdparty/QXlsx
cd thirdparty/QXlsx
git checkout 700bda6a83f675ed1d2d8d359b23f18619dd64c7   # "Make qHash compatible with Qt6 signature" (v1.5.0-17-g700bda6)
cd ..\..
```

**Recommended fix (developers):** update the `url` in `.gitmodules` to the
QtExcel location and run `git submodule sync`.

### Pitfall 2 — Utilities submodule can be left with an empty working tree

During the initial `submodule update`, the abort caused by Pitfall 1 left the
`Utilities` submodule checked out but with every source file staged as deleted
(empty working tree). CMake then failed with
`Cannot find source file: Utilities/Distribution.cpp`.

**Workaround used:**

```powershell
git submodule update --init --force Utilities
cd Utilities
git checkout --force 5db8d1464ab3a1cfcccedfd40e7135da0b11025b   # "Update utilities code"
cd ..
```

### Pitfall 3 — Armadillo requires BLAS/LAPACK to be discoverable

Initial CMake configure failed with:

```
Could NOT find Armadillo (missing: LAPACK_FOUND BLAS_FOUND)
```

conda-forge's Armadillo headers were found, but `FindArmadillo.cmake` requires
BLAS and LAPACK to resolve. **Fix:** `libblas`, `liblapack`, and `openblas` are
already declared in the `pixi.toml` you created in Phase A (Appendix A), so this
resolves automatically. (Documented here because it is the *reason* those three
packages are in the dependency list.)

### Pitfall 4 — Armadillo SuperLU wrappers unresolved at link time (Windows-specific)

After all 101 translation units compiled, linking failed with 10 unresolved
externals:

```
LNK2019: unresolved external symbol wrapper_dgssv  (and wrapper_dgssvx,
wrapper_StatInit, wrapper_StatFree, wrapper_set_default_options,
wrapper_Destroy_*, wrapper_superlu_malloc, wrapper_superlu_free)
LNK1120: 10 unresolved externals
```

Root cause: the shared `Utilities` submodule hard-codes
`#define ARMA_USE_SUPERLU 1` in `Matrix_arma.cpp` and `Matrix_arma_sp.cpp`,
which pulls in Armadillo's SuperLU sparse-solver backend. **conda-forge has no
`superlu` package for `win-64`** (it resolves for linux-64/osx only — "No
candidates were found for superlu"). This is likely *why* the software targets
macOS/Linux only.

Verification before working around it: the sparse-matrix class
(`CMatrix_arma_sp`) is used **only inside the `Utilities` submodule**.
SedSAT3's own scientific code (conductor, GA, MCMC, `sourcesinkdata`) uses only
the *dense* `solve_ar` on `CMatrix`/`CMatrix_arma`. So disabling SuperLU does
not affect the sediment-apportionment computations.

**Workaround used (local, uncommitted, reversible):** guard the define so
SuperLU is enabled only on non-Windows platforms, keeping Linux/macOS behavior
identical:

```cpp
// Utilities/Matrix_arma_sp.cpp and Utilities/Matrix_arma.cpp
#if !defined(_WIN32)
#define ARMA_USE_SUPERLU 1
#endif
```

**Note for developers:** this change belongs upstream in the `Utilities`
repository if Windows support is desired. It was made in the submodule working
tree only and is not committed. **It is also not covered by Phase A** — if you
rebuild from a pristine `Utilities` checkout you must re-apply it by hand.

### Pitfall 5 — Runtime DLLs not found (double-click fails)

The linked exe depends on DLLs that live in the pixi env's `Library\bin`, not
next to the exe: `openblas.dll`, `gsl-28.dll`, `Qt6Charts.dll`, `Qt6Core.dll`,
etc. Double-clicking the exe fails (or, worse, silently loads a mismatched DLL
found elsewhere on PATH).

Two solutions:

1. **Reliable / recommended — run inside the activated env:**
   `pixi run run-app`. Pixi prepends `Library\bin` to PATH so every DLL and its
   transitive dependencies resolve from one consistent environment.

2. **Portable — stage DLLs next to the exe:** `pixi run deploy-win` runs
   `windeployqt6` (which also copies the essential Qt **plugins**, notably
   `platforms\qwindows.dll`, without which no Qt GUI app can start) and copies
   the numerical DLLs.

### Pitfall 6 — Visual C++ redistributable not bundled

`dumpbin /dependents` on the exe also lists `MSVCP140.dll`,
`VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`, and `VCOMP140.dll` (the last is the
OpenMP runtime, required because the app links OpenMP). These come from the VS
install and are present in a developer shell, but a bare double-click on a
machine without the VC++ redistributable would fail. They were copied from:

```
C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Redist\MSVC\<ver>\x64\
    Microsoft.VC143.CRT\    -> MSVCP140.dll, VCRUNTIME140.dll, VCRUNTIME140_1.dll
    Microsoft.VC143.OpenMP\ -> VCOMP140.dll
```

After staging Qt DLLs + plugins, numerical DLLs, and the VC++ runtime, the exe
was verified to launch with a **minimal PATH** (`C:\Windows\System32` only),
confirming `build\bin` is self-contained.

## Static analysis with pixi (clang-tidy + cppcheck)

> **Reminder:** on a fresh clone neither the static-analysis *tasks* nor the
> `.clang-tidy` config exist — both are created in Phase A (Appendices A and B).
> Unlike the original upstream `pixi.toml`, which the review found *declared*
> `clang-tools` and `cppcheck` under `[dependencies]` but never invoked them,
> the Appendix A file both declares the packages **and** wires up the tasks
> below.

### Tasks (defined in the Appendix A `pixi.toml`)

```toml
[tasks]
# configure also emits build/compile_commands.json for clang-tidy:
configure = "cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON"

# clang-tidy over the scientific core; depends on configure (needs the DB):
lint = { cmd = "clang-tidy -p build src/sourcesinkdata.cpp src/conductor.cpp ...", depends-on = ["configure"] }

# cppcheck over src/ + include/; self-heals its config dir first (see below):
_cppcheck-stage-cfg = "cmake -E copy_directory .pixi/envs/default/share/Cppcheck/cfg .pixi/envs/default/Library/bin/cfg"
cppcheck = { cmd = "cppcheck --enable=warning,performance,portability --std=c++17 --language=c++ -I include --suppress=missingIncludeSystem src include", depends-on = ["_cppcheck-stage-cfg"] }

# run both:
check = { cmd = "cppcheck ...", depends-on = ["lint", "_cppcheck-stage-cfg"] }
```

Run them from a **Developer PowerShell for VS 2022** (clang-tidy needs the MSVC
headers referenced by the compilation database):

```powershell
pixi run cppcheck    # fast; standalone
pixi run lint        # slower; sourcesinkdata.cpp is ~188 KB
pixi run check       # both
```

### Incantation 1 — cppcheck can't find `std.cfg` (conda-forge win-64 bug)

Out of the box, `pixi run cppcheck` aborts immediately:

```
cppcheck: Failed to load library configuration file 'std.cfg'. File not found
Failed to load std.cfg. Your Cppcheck installation is broken, please re-install.
The Cppcheck binary was compiled with FILESDIR set to
"D:/bld/bld/rattler-build_cppcheck_1780645852/h_env/share/Cppcheck" ...
```

**Root cause:** the conda-forge `win-64` cppcheck 2.21.0 package bakes its
`FILESDIR` (the compiled-in config search path) to the *build server's* path
(`D:/bld/...`). At startup cppcheck unconditionally loads `std.cfg` from
`FILESDIR/cfg`, which does not exist on your machine, and aborts. In the pixi
env the cfg files actually live at:

```
.pixi/envs/default/share/Cppcheck/cfg/std.cfg
```

**Dead ends (do not bother):** in 2.21.0 neither of these redirects the startup
lookup —
- a runtime `FILESDIR` environment variable (it's a *compile-time* setting), nor
- CLI flags `--data-dir=` (unrecognized in this version) or `--library=<path>`
  (the `std.cfg` failure happens *before* `--library` args are processed).

**Working incantation:** cppcheck also searches for its cfg relative to the
executable, at `<exedir>/cfg`. The exe is at
`.pixi/envs/default/Library/bin/cppcheck.exe`, so staging the cfg files into
`.pixi/envs/default/Library/bin/cfg` makes the startup load succeed. The
`_cppcheck-stage-cfg` helper task does exactly this with
`cmake -E copy_directory` (cross-platform, idempotent). Because `cppcheck` and
`check` depend on it, the copy is recreated automatically — it **self-heals**
after `pixi clean` or a fresh env install, and the staged copy lives under
`.pixi/` (gitignored), so nothing extra is committed.

> Note: this is a **Windows-only** packaging quirk. The linux-64/osx cppcheck
> packages ship a correct `FILESDIR` and need none of this.

### Incantation 2 — clang-tidy runs "no checks enabled"

Out of the box, `pixi run lint` configures fine, generates the compilation
database, launches clang-tidy — and then errors:

```
Error: no checks enabled.
```

**Root cause:** clang-tidy enables **zero** checks by default. It expects either
a `--checks=...` argument or a `.clang-tidy` config file it can auto-discover.
A fresh clone has neither — which is exactly why Phase A step A.3 creates the
`.clang-tidy` file (Appendix B).

**Working incantation:** the `.clang-tidy` file at the repo root declares the
check selection (clang-tidy walks parent directories to find it), so the `lint`
task needs no `--checks` on the command line. The selection is deliberately
focused (not `*`) to keep the first pass actionable, and notably enables
`concurrency-*` (including `concurrency-mt-unsafe`) which targets the
`rand()`/`srand()`-inside-OpenMP finding in `CODE_REVIEW_OBSERVATIONS.md` §11.

Validate the config without running an analysis:

```powershell
pixi run clang-tidy --verify-config
```

(One gotcha found this way: a guessed check name that doesn't exist in this
clang-tidy version is reported as `unknown check '...'` — remove it and
re-verify.)

## Appendix A — `pixi.toml` (create at repo root in Phase A)

Create this file **verbatim** at the repository root. It does not exist in a
fresh clone of `ce7bc1d`.

```toml
[workspace]
name = "sedsat3"
version = "1.1.6"
description = "Pixi environment for building SedSAT3 (Qt6 / Armadillo / GSL / OpenMP)"
channels = ["conda-forge"]
platforms = ["win-64", "linux-64", "osx-64", "osx-arm64"]

[dependencies]
cmake = ">=3.16"
ninja = "*"
qt6-main = "*"      # provides Qt6 Core, Gui, Widgets, PrintSupport
qt6-charts = "*"    # Qt6 Charts (required by USE_QCHARTS)
armadillo = "*"
libblas = "*"       # BLAS (required by Armadillo)
liblapack = "*"     # LAPACK (required by Armadillo)
openblas = "*"      # concrete BLAS/LAPACK implementation
gsl = "*"
clang-tools = "*"   # clang-tidy (static analysis, incl. concurrency-mt-unsafe)
cppcheck = "*"      # complementary static analyzer

# On Windows the compiler comes from MSVC (VS 2022). conda-forge supplies the
# libraries + CMake/Ninja. On Linux/macOS, uncomment the compilers below to get
# a fully self-contained toolchain from conda-forge.
# [target.linux-64.dependencies]
# cxx-compiler = "*"
# [target.osx-64.dependencies]
# cxx-compiler = "*"
# [target.osx-arm64.dependencies]
# cxx-compiler = "*"

[tasks]
configure = "cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON"
build = { cmd = "cmake --build build --parallel", depends-on = ["configure"] }
clean = "cmake -E rm -rf build"

# --- Debug / diagnostic build ---------------------------------------------
# A separate build tree (build-debug/) with debug symbols, kept apart from the
# Release build/ so the two never collide (mixing configs in one CMake tree is
# fragile). Purpose: get a faithful, symbolicated stack trace for runtime
# crashes (e.g. the Distribution Fitting null-deref investigation).
#
# NOTE ON BUILD TYPE (MSVC-specific): this uses RelWithDebInfo, NOT Debug, on
# purpose. A full MSVC `Debug` build links the *debug* CRT (/MDd) and expects
# debug runtime DLLs, but the conda-forge Qt/OpenBLAS/LAPACK/GSL dependencies
# are built against the *release* CRT. Mixing them produces its own crashes
# unrelated to the bug under investigation. RelWithDebInfo gives full debug
# symbols (/Zi + .pdb) and disables optimization inlining enough for a readable
# stack trace, while keeping the release CRT so it stays ABI-compatible with the
# conda-forge DLLs. To force lower optimization for even cleaner traces, the
# configure step below sets -O_d-style flags via CMAKE_CXX_FLAGS_RELWITHDEBINFO.
configure-debug = "cmake -B build-debug -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_CXX_FLAGS_RELWITHDEBINFO=\"/Zi /Od /Ob0 /DNDEBUG\""
build-debug = { cmd = "cmake --build build-debug --parallel", depends-on = ["configure-debug"] }
clean-debug = "cmake -E rm -rf build-debug"

# --- Static analysis -------------------------------------------------------
# These wire up the clang-tools (clang-tidy) and cppcheck packages already
# declared under [dependencies]. Scope is the scientific core in src/ +
# include/ (the review-relevant surface), deliberately excluding the flat
# root-level Qt GUI/moc files, which are noisier and less analysis-relevant.
#
# clang-tidy reads compile flags/includes from build/compile_commands.json,
# which `configure` now emits (-DCMAKE_EXPORT_COMPILE_COMMANDS=ON), hence the
# depends-on. cppcheck does its own parsing and needs no compilation database.

# clang-tidy over the core translation units. Uses the compilation database.
lint = { cmd = "clang-tidy -p build src/sourcesinkdata.cpp src/conductor.cpp src/elemental_profile.cpp src/elemental_profile_set.cpp src/concentrationset.cpp src/cmbdistribution.cpp src/parameter.cpp src/observation.cpp src/interface.cpp src/GA/GA.cpp src/GA/Individual.cpp src/GA/GADistribution.cpp src/GA/Binary.cpp", depends-on = ["configure"] }

# cppcheck as a complementary analyzer (standalone; no compile DB required).
# --enable=warning,performance,portability keeps the signal-to-noise reasonable
# for a first pass; drop `style` in to be stricter. -I include supplies headers.
#
# WORKAROUND: the conda-forge win-64 cppcheck package bakes FILESDIR to the
# build server's path (D:/bld/...), so at startup it cannot find its bundled
# std.cfg and aborts. Neither a runtime FILESDIR env var nor CLI flags redirect
# that startup lookup in cppcheck 2.21.0. The reliable fix is cppcheck's
# executable-relative fallback: it also searches <exedir>/cfg. The helper task
# below stages the env's cfg files there. It is idempotent (safe to re-run) and
# self-heals after `pixi clean` / a fresh env install, so cppcheck is
# reproducible without manual steps. The staged copy lives under .pixi/ and is
# gitignored, so nothing is committed.
_cppcheck-stage-cfg = "cmake -E copy_directory .pixi/envs/default/share/Cppcheck/cfg .pixi/envs/default/Library/bin/cfg"

cppcheck = { cmd = "cppcheck --enable=warning,performance,portability --std=c++17 --language=c++ -I include --suppress=missingIncludeSystem src include", depends-on = ["_cppcheck-stage-cfg"] }

# Convenience: run both analyzers (clang-tidy then cppcheck).
check = { cmd = "cppcheck --enable=warning,performance,portability --std=c++17 --language=c++ -I include --suppress=missingIncludeSystem src include", depends-on = ["lint", "_cppcheck-stage-cfg"] }

# Launch the built app inside the activated pixi environment. This puts
# .pixi/envs/default/Library/bin on PATH, so every runtime DLL (Qt, OpenBLAS,
# LAPACK, GSL) and its transitive dependencies resolve from one consistent env.
run-app = "build/bin/SedSat3.exe"

# Launch the debug/diagnostic build. Same environment activation as run-app,
# but points at build-debug/. Run any crash repro here so the console breadcrumbs
# and the debugger stack trace carry file/line info from the .pdb symbols.
run-app-debug = "build-debug/bin/SedSat3.exe"

# Windows: stage Qt runtime DLLs + plugins (via windeployqt) and the numerical
# runtime DLLs (BLAS/LAPACK/GSL) next to the built executable so it runs
# standalone. Run after `build`, from a VS developer shell.
#
# NOTE: split into two steps (windeployqt, then the DLL copy) chained by
# depends-on, and each `cmd` is a SINGLE LINE. An earlier version chained them
# with `&&` inside a multi-line triple-quoted string; depending on the pixi/
# shell version the embedded newlines were re-tokenized so that each DLL path
# on its own line became a separate command (cmake printed its -E usage, and the
# runner tried to *launch* openblas.dll -> "os error 193"). Keeping the copy on
# one line passes all DLL paths as arguments to a single `cmake -E copy_if_different`.
_deploy-win-qt = "windeployqt6 --qtpaths .pixi/envs/default/Library/bin/qtpaths6.exe --release --no-translations --compiler-runtime build/bin/SedSat3.exe"
deploy-win = { cmd = "cmake -E copy_if_different .pixi/envs/default/Library/bin/openblas.dll .pixi/envs/default/Library/bin/libblas.dll .pixi/envs/default/Library/bin/libcblas.dll .pixi/envs/default/Library/bin/liblapack.dll .pixi/envs/default/Library/bin/gsl-28.dll .pixi/envs/default/Library/bin/libwinpthread-1.dll .pixi/envs/default/Library/bin/libomp.dll .pixi/envs/default/Library/bin/libiomp5md.dll build/bin/", depends-on = ["_deploy-win-qt"] }

# Windows: same as deploy-win but stages the runtime next to the debug build.
# windeployqt still uses --release here because the conda-forge Qt DLLs are the
# release builds (RelWithDebInfo links against them, see configure-debug note);
# passing --debug would make windeployqt look for debug Qt DLLs that aren't
```
